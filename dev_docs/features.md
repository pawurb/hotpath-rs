# Features Reference

Where to find the authoritative definitions, plus behavior gotchas that the code can't show at a glance. See `CLAUDE.md` for project guidance.

## Sources of truth

- **Feature flags**: `[features]` in `crates/hotpath/Cargo.toml`. User-facing descriptions are spread across the per-subsystem pages in `docs/src/` (see `SUMMARY.md` for the index); `profiling_modes.md` covers only the profiling-mode flags (`hotpath`, `hotpath-alloc`, ...).
- **Attribute macros** (`#[main]`, `#[measure]`, `#[measure_all]`, `#[skip]`, `#[future_fn]`) and their parameters: `crates/hotpath-macros/src/lib.rs` (doc comments on each `#[proc_macro_attribute]`).
- **Declarative macros** (`measure_block!`, `dbg!`, `val!`, `gauge!`, `tokio_runtime!`): `crates/hotpath/src/lib_on.rs`. Wrapper macros (`channel!`, `stream!`, `future!`, `rw_lock!`, `mutex!`, `http!`, `axum!`, `io!`): `#[macro_export]` in the matching `crates/hotpath/src/lib_on/<subsystem>.rs`. Every macro has a no-op twin in `lib_off.rs`.
- **Builder API**: `HotpathGuardBuilder` in `crates/hotpath/src/lib_on/hotpath_guard.rs` (defaults live in its field initializers).
- **Environment variables**: user-facing reference in `docs/src/configuration.md`; discover parse sites with `grep -rn 'HOTPATH_' crates/hotpath/src crates/hotpath/bin` (main site: `lib_on/hotpath_guard.rs`; TUI vars in `bin/hotpath/cmd/console*`; CPU vars in `lib_on/functions/cpu/`).
- **Usage examples**: every `crates/test-*` example's top comment contains its exact cargo command (usually a `//! Run with:` header).

## Running examples

```bash
cargo run -p test-tokio-async --features=hotpath --example basic
cargo run -p test-tokio-async --features='hotpath,hotpath-alloc' --example basic   # + alloc profiling
cargo run -p test-smol-async --features=hotpath --example basic_smol               # non-tokio runtime
```

## Gotchas (not obvious from signatures)

Features:
- `tokio` is only for tokio-specific integrations (tokio channels/locks, async `io!` traits, `tokio_runtime!()`). Async function profiling itself is runtime-agnostic and needs no feature.
- `sqlx`/`toasty` layers pull in no sqlx/toasty dependency - they are generic `tracing` layers reading event fields (`sqlx::query` / `toasty::query` targets; don't globally filter those out). One sqlx layer covers 0.8 and 0.9. Toasty key-value (DynamoDB) ops carry no SQL and are skipped.
- `json` (`dep:serde` + `dep:serde_json`) gates `hotpath::json` (report types, `Route`) and the `output.rs` format/parse helpers; implied by `hotpath`, `utils`, `tui`. Enable it alone to parse `JsonReport`s in a consumer (the hotpath.rs backend) without pulling the profiler in.
- `demo` implies `hotpath` and pulls sqlx/diesel/reqwest clients only for the TUI demo, never in plain `tui` or library builds.
- `hotpath-cloud` (`lib_on/cloud.rs`, not user-documented yet) does not imply `hotpath`; with `hotpath` on it uploads the `JsonReport` from `HotpathGuard::drop` to hotpath.rs when `HOTPATH_UPLOAD=1`, via a sync `ureq` client (the guard may outlive the tokio runtime). Needs `ACTIONS_ID_TOKEN_REQUEST_URL`/`_TOKEN` (GitHub Actions with `id-token: write`), otherwise prints a skip line. `HOTPATH_BENCHMARK` names the series (default `default`); names are validated (1-64 chars from `[A-Za-z0-9._-]`, not `.` or `..`) and an invalid name skips the upload with a stderr message instead of failing the run. The server enforces the same rule (400); keep both byte-for-byte identical. The base URL is hard-coded to `https://hotpath.rs`. Upload is additive to the configured output format and never affects the exit code. The uploaded report ignores display limits: the `limit_for` closure in `HotpathGuard::drop` substitutes `cloud::UPLOAD_LIMIT` (`HOTPATH_UPLOAD_LIMIT`, default `0` = unlimited, one value for every section) for `HOTPATH_LIMIT`/`HOTPATH_<SECTION>_LIMIT`/builder limits whenever the cloud path is on, because the server diffs reports by entry name and cannot un-truncate a client-side top-N. Since one `JsonReport` feeds both the JSON writer and the upload, a run with `HOTPATH_OUTPUT_FORMAT=json` and `HOTPATH_UPLOAD=1` also writes the full lists locally (table output is a separate path and is unaffected). `debug` has no display limit, so the guard passes it `limit_for(0)` and only the upload limit can cap it. Every section list (`Json*List`, including `threads` and `debug`) carries required `total_count` (entries measured) and `included_count` (entries in `data`, always `data.len()`) fields so consumers can tell a truncated list from a complete one; the `collect_*_json` builders in `lib_on/report.rs` take the full entry slice plus a limit and truncate themselves, and the live metrics-server builders pass limit `0`. The feature also enables `hdrhistogram/serialization` + `base64`: when `HOTPATH_UPLOAD=1`, every hdrhistogram-backed entry in the final report carries its raw histogram(s) as base64 HdrHistogram V2-deflate fields (`None` when nothing was sampled) - `histogram` on `functions_timing`, `functions_alloc` (bytes or alloc counts per `HOTPATH_ALLOC_METRIC`, `None` for async entries), `sql`, `http`, `server`, and per-op `io` stats; `proc_histogram` on `channels` (wrap channels only); `wait_histogram`/`acquire_histogram` on `mutexes`; `read_wait_histogram`/`write_wait_histogram`/`read_acquire_histogram`/`write_acquire_histogram` on `rw_locks`. Values are ns except `functions_alloc`. Gated for functions by `FunctionStatsConfig::histograms` and for the other sections by a `histograms: bool` parameter on the `collect_*_json` builders; both are `false` on the live metrics-server path so the TUI never receives them, and table-format re-builds also pass `false`. Encoder lives in `lib_on/histograms.rs::histogram_base64`.
- Report `location` fields (`lib_on/locations.rs`): every macro registers a static `Location { file, line, column }` under the same identity string the stats use (function name / label for the attribute macros, `file:line:column` call-site id for every resource macro - `channel!`/`stream!`/`io!`/`mutex!`/`rw_lock!`/`future!`/`dbg!`/`val!`/`gauge!` - with the user-visible `source` stripped back to `file:line`); JSON builders join on that string at build time and attach a `location` object - required on resource entries (`channels`, `streams`, `futures`, `rw_locks`, `mutexes`, `io`; the deprecated `wrap::*::new()` constructors register a leaked runtime `Location::caller()` so the invariant holds there too, and `location_for_key` falls back to parsing the id string if the registry is ever unavailable), optional where absence is semantically real: `functions_timing`/`functions_alloc` entries and function-log lists (a bare `HotpathGuardBuilder` wrapper registers nothing), `debug` (`val!` with no logs), and `sql`/`http` (query issued outside any measured scope has no caller). Emitted unconditionally (static report and live metrics path), unlike histograms. First registration wins: call sites sharing one label already merge into one stats entry. `file` is normalized at build time: relative paths pass through, cargo-registry paths become `<external>/<crate>-<version>/...`, other absolute paths pass through. `#[measure]`/`#[main]`/`#[future_fn]` span the `file!()`/`line!()` tokens to the fn ident (`quote_spanned!`) so the line points at the `fn` item, not the attribute.
- Report `meta` object (`lib_on/report_meta.rs`, filled in `HotpathGuard::drop` for JSON/cloud reports): `rustc` (from the crate's `build.rs`), `os`, `created_at` (RFC 3339 UTC), `source_root` (build workspace root relative to the enclosing git root - the checkout is resolved as the nearest working-dir ancestor containing a registered relative source file, since `file!()` is workspace-root-relative, not cwd-relative; `HOTPATH_SOURCE_ROOT` overrides, and the field is omitted rather than guessed when resolution fails - nested workspace launched from above it, run outside the checkout, no git root), and - only with `hotpath-cloud` - `git`, `ci` and `benchmark` (see below). The top-level `version` field stays the crate-version source of truth; `meta` never duplicates it.
- Report git/CI provenance (`hotpath-cloud` only) makes an uploaded report self-describing, so the server does not have to reconstruct context from a GitHub Actions OIDC token - which CLI uploads, non-GitHub providers and relayed uploads have no way to supply. Every field is optional and `skip_serializing_if`, so old and new clients/servers interoperate in both directions.
  - `meta.git` (`lib_on/git_info.rs`): `sha`/`ref` read from the resolved checkout's `.git`, never shelling out; handles worktree/submodule `gitdir:` files and `packed-refs`; `repository` ("owner/name") parsed from the `origin` remote URL in `.git/config` (SSH and HTTPS forms). Omitted when the checkout cannot be resolved so an unrelated repo's HEAD is never reported, except that a `HOTPATH_SOURCE_ROOT` override asserts the runtime checkout is the source checkout and re-enables cwd-based git discovery. `base_sha` stays `None` locally: a `merge-base(HEAD, <default branch>)` needs a commit-graph walk this pure `.git` reader deliberately avoids.
  - `meta.ci` (`lib_on/ci_info.rs`): `provider` is the discriminator ("github-actions" today), the rest (`event`, `pull_request`, `run_id`, `workflow`, `actor`, `repository_id`) provider-neutral, so a new CI system is a change in that one file. Detected from `GITHUB_ACTIONS=true`; values from `GITHUB_SHA`/`GITHUB_REF`/`GITHUB_REPOSITORY`/`GITHUB_REPOSITORY_ID`/`GITHUB_EVENT_NAME`/`GITHUB_BASE_REF`/`GITHUB_HEAD_REF`/`GITHUB_RUN_ID`/`GITHUB_WORKFLOW`/`GITHUB_ACTOR`.
  - `ci.provider` and `ci.event` are required, `event` holding the raw provider event name. Deliberately strings and not enums: an event we do not model (`workflow_dispatch`, `schedule`, `merge_group`) has to round-trip rather than fail the whole report on deserialize, and a catch-all enum variant would need `#[serde(untagged)]` on a variant (serde >= 1.0.181, above the declared floor). `detect()` omits `ci` entirely rather than inventing a placeholder when `GITHUB_EVENT_NAME` is unset. `run_id`/`workflow`/`actor`/`repository_id` stay optional: forcing them to `String` would only turn an absent variable into `""`, which is a worse `None`.
  - `ci.pull_request` (`JsonPullRequest`) groups `number`, `base_ref` and `head_ref`, present exactly when `event == "pull_request"`. They were never independently optional - a pull request always has all three - so `Option<JsonPullRequest>` states the real invariant, and the server's "`pr_number` and `base_ref` required on PR uploads" rule becomes one check instead of two. `base_ref`/`head_ref` are bare branch names ("main", "feature-x"), not refs; the server needs `base_ref` as the branch-level baseline when no report exists for `git.base_sha`, and `head_ref` for the PR comment header, which would otherwise read `refs/pull/<n>/merge`.
  - `number` is parsed from `GITHUB_REF` (`refs/pull/<n>/merge`) before falling back to the event file, so all three grouped fields are environment-derived. Without that the grouping would regress: an unreadable payload would cost `base_ref` as well as `git.base_sha`, and `base_ref` is exactly the fallback for that missing sha - one failure would take out both the primary and its backup.
  - `merge_git_info` in `lib_on/report_meta.rs`: **the checkout is the commit identity, the environment only describes the run.** `sha` is `.git` HEAD, falling back to `GITHUB_SHA` when `.git` is unreadable; `GITHUB_REF` is applied only when `GITHUB_SHA == sha`, i.e. when the environment actually describes what was built, and `git.repository` prefers the `origin` remote over `GITHUB_REPOSITORY`. The event file's `base_sha` gets a narrower guard than the ref does - it is dropped only when it equals `sha`: the pull request's base is the right baseline for the merge commit and the head commit alike, so a job that checked out `pull_request.head.sha` (common, to avoid benchmarking the synthetic merge) keeps it, while only a job that checked out the base commit itself is measuring the base and has nothing to compare against. Gating `base_sha` on `GITHUB_SHA == sha` instead would silently drop a correct baseline on head checkouts and leave the server to fall back to `ci.base_ref`, which resolves to whatever the branch tip is by then. A job may check out something else - `actions/checkout` with `ref: <pull_request.head.sha>`, or the mid-job `git checkout <base sha>` in `docs/src/github_ci.md` - while `GITHUB_SHA` stays pinned to the merge commit, so preferring the environment would attribute measurements to a commit that was never compiled. Conversely a default PR checkout is detached, so when the environment does match it is the only source of a ref. `ci.*` is environment-only and unguarded: a `pull_request` run is a `pull_request` run whatever it checked out. Do not add a "warn when `git.sha != claims.sha`" cross-check on the server - under this rule that mismatch is by design.
  - `git.base_sha` on a pull request run comes from the `pull_request.base.sha` in the JSON file at `$GITHUB_EVENT_PATH` (`pr_number` from `pull_request.number` in the same file), read only when `GITHUB_EVENT_NAME == "pull_request"`. That file is written once when the event fired, so it and `GITHUB_SHA` describe the same snapshot by construction - a REST lookup would answer with the PR's base *as of now*, which drifts while a benchmark runs. Parsed with a tolerant struct, all-or-nothing per payload: a malformed `pull_request` object loses `pr_number` and `base_sha` together. A missing var, unreadable file or unexpected shape omits the fields and never fails the run.
  - `meta.benchmark` mirrors `cloud.rs::benchmark_name()` (`HOTPATH_BENCHMARK`, default `default`) and is set on every report, not only uploads. `cloud.rs` still sends the `?benchmark=` query parameter; the server prefers `meta.benchmark` and falls back to the parameter.
  - None of this is authorization: the server derives the repository from the upload credential. `ci.repository_id` is compared against the verified claim (mismatch rejected as a misdirected upload) and `git.repository` mismatches only warn, since a rename keeps the id but changes the name.
  - The server treats the report as the *only* source of run context, with no fallback to the OIDC claims, so `git.sha` is required and `ci.pr_number`/`ci.base_ref` are required on `pull_request` uploads (a missing one is a 400, not a silent degradation). This client release therefore has to ship before the backend starts requiring them.
  - Not user-documented: `meta.git.*`, `meta.ci.*` and `meta.benchmark` are all cloud-only, so they stay in `dev_docs/` and out of the mdBook under `docs/` until cloud ships. `docs/src/configuration.md` mentions `meta.git` only in passing, in its pre-existing `HOTPATH_SOURCE_ROOT` row.

Macros:
- `#[measure]` `label = "..."`: duplicate labels panic at runtime. `impl_type = "Type"` is required for correct `hotpath-cpu` attribution on bare-annotated impl methods (`#[measure_all]` on inherent impls auto-injects it; trait impl methods never match, see `dev_docs/architecture.md`).
- `channel!`: `futures_channel::mpsc` is forwarder-only (`proxy = true`) and bounded variants need `capacity = N`. Bounded `std::sync::mpsc::sync_channel` also requires `capacity = N` matching the constructor argument (std exposes no capacity accessor; the wrapper rebuilds the channel) - omitting it panics at runtime.
- `channel!`/`stream!` default to one entry per `(call site, message/item type)` - repeat registrations reuse the cached id from `CHANNEL_SOURCE_IDS` (`channels.rs`) / `STREAM_SOURCE_IDS` (`streams.rs`) and only bump the entry's `Inst` count, so state stays bounded by call-site count. `iter = true` gives per-instance rows (suffixed `label-2`, `label-3`, ...) - unbounded instance churn then grows profiler state, same tradeoff as `io!`. The first registration's `label` and `channel_type` win for the aggregated entry; a variable-capacity expression at one call site is recorded under the first capacity seen.
- `http!`: times reqwest's `execute` future, which resolves when response headers arrive - body download is excluded. The `hotpath::wrap::reqwest::Client` alias resolves to `ClientWithMiddleware` with profiling on and the raw client with it off. For ureq (`ureq-3` feature) the macro takes a `ConfigBuilder<AgentScope>` and returns it with `UreqHttpMiddleware` appended (ureq only accepts middleware at config-build time; no type alias needed since the type is unchanged). ureq's `Error::StatusCode` is mapped back to a status so 4xx/5xx aren't miscounted as transport errors; an explicit scheme-default port (`:443`/`:80`) is dropped from the endpoint key because `Uri::port_u16` keeps it. Any new HTTP/SQL front-end feature must be added to the `cfg_if!` gates in `lib_on/caller_stack.rs` and `lib_on/functions.rs` (`await_with_caller_scope`) or the `Source` column stays empty.
- `axum!` (`axum-0-8`): expands to `router.layer(AxumLayer::new())`, so it must wrap the finished router - `Router::layer` ignores routes added afterwards. `AxumLayer` is a hand-written tower `Layer`/`Service` (`lib_on/server/axum_08.rs`, generic over request/response bodies), not `from_fn`, so no per-request boxing. Route key is `METHOD MatchedPath`; `MatchedPath` is absent for fallbacks and `nest_service` targets, in which case the raw path goes through `http::normalize::normalize_endpoint`. Timing stops when the response head is produced (body streaming excluded, symmetric with `http!`). Server logs reuse `HttpLogEntry`/`JsonHttpLogsList`; the TUI Server subtab reuses the HTTP logs pane state. Route scoping: `AxumResponseFuture::poll` enters `caller_stack::enter_route` (a save/restore thread-local `Cell`, separate from the caller stack) around the inner poll, and SQL/HTTP front-ends read `current_route()` next to `current_caller()`; `route` is the first element of the `SqlKey`/`HttpKey` tuple and the `Route` column renders only when some entry has one. Only matched templates are interned to `&'static str` (`intern_route`, capped at `HOTPATH_ENTRIES_LIMIT`; templates past the cap get no route context) - unmatched raw paths never enter the interner. `stop_server_events` turns scoping off so post-shutdown requests stop interning. `HOTPATH_ROUTE_SCOPE=0` / `route_scope(false)` is resolved in `HotpathGuardBuilder::build`, so a layer created before the guard still honors it at request time.
- `io!`: derefs to the wrapped value; `hotpath::io_unwrap(x)` peels the wrapper for consuming methods (identity with profiling off). `Seek`/`BufRead` delegation is not instrumented. `iter = true` gives per-instance rows - unbounded instance churn then grows profiler state.
- All guards are `#[must_use]`.

Env vars:
- `HOTPATH_KEEP_INLINE` is read at proc-macro expansion time - touch source or `cargo clean` after toggling.
- `HOTPATH_ALLOC_METRIC` panics on values other than `bytes`/`count`. `HOTPATH_ALLOC_CUMULATIVE` produces invalid results for recursive functions.
- `HOTPATH_SQL_RAW_LOGS` is off by default so bound literals (potentially sensitive) never reach the logs.
- `HOTPATH_TIME_SAMPLING_RATE=0.0` gives count-only mode (durations and io `Rate` show `-`). Per-resource `HOTPATH_<RESOURCE>_TIME_SAMPLING_RATE` variants take precedence.
- `HOTPATH_PROMETHEUS_FAST_BUCKETS` / `HOTPATH_PROMETHEUS_SLOW_BUCKETS` replace the classic ladders (`prometheus_server.rs`, `FAST_LADDER_NS` / `SLOW_LADDER_NS` LazyLocks, forced in `start_prometheus_server` so bad input panics on the main thread, not on first scrape inside a worker). Seconds, strictly ascending after rounding to ns, capped at `MAX_DURATION_NS`.
- CPU report has no dedicated limit var - it uses `HOTPATH_FUNCTIONS_LIMIT` (fallback `HOTPATH_LIMIT`); wrapper `caller_name` is exempt.

## GitHub CI Integration

`hotpath-utils profile-pr` compares PR branch metrics against base and posts a diff comment. Two-workflow setup (`hotpath-profile` + `hotpath-comment`) for fork security; see `docs/src/github_ci.md`.
